# Обучающий датасет

Скрипт `scripts/generate_dataset.py` генерирует пары «пространственный
контур → минимальная поверхность». Для каждого контура вызывается собранный
CLI `triangulation`, а результирующая OBJ-сетка становится
целевой поверхностью для обучения условной модели неявного поля.

Запуск небольшого проверочного набора:

```bash
cmake --build build -j2
python3 scripts/generate_dataset.py --smoke --output-dir /tmp/triangulation-smoke
```

Обычный запуск, например:

```bash
python3 scripts/generate_dataset.py \
  --samples 32 --seed 1234 --boundary-size 64 --queries 8192 \
  --refine 2 --output-dir dataset
```

Для больших наборов используется отдельный возобновляемый многопроцессный
скрипт `scripts/generate_dataset_parallel.py`. Рекомендуемый запуск на 100 000
пар, устройство каталога, журнал ошибок и локальный benchmark описаны в
[`LARGE_DATASET_RU.md`](LARGE_DATASET_RU.md).

По умолчанию учитель работает в режиме `graph`: для контуров с выпуклой
XY-проекцией он устойчиво строит сгущённые цели. Экспериментальный
`--solver-mode spatial` свободно двигает внутренние вершины по XYZ, но после
автоматического сгущения веерной начальной сетки может не сойтись. Для него
по умолчанию используются три прохода remeshing, для `graph` — ноль.

Если бинарник находится в другом месте, его можно передать явно через
`--solver PATH`. Исходные контуры строятся конечными Fourier-разложениями.
Выпуклая, но не обязательно эллиптическая XY-проекция задаётся через support
function; это даёт разнообразие формы и одновременно сохраняет класс входов,
надёжно обрабатываемый текущим `graph`-решателем. Fourier-профиль по Z задаёт
непланарность. Флаги `--fourier-modes`, `--fourier-decay`, `--xy-variation` и
`--nonplanarity` управляют спектром, а `--min-separation` и `--max-curvature`
отбрасывают плохие дискретизации. Перед вызовом решателя контур ресемплируется,
центрируется и поворачивается так, чтобы его векторная площадь была направлена
точно вдоль `+Z`. Затем он масштабируется внутрь единичного куба с
десятипроцентным запасом. Если после поворота XY-проекция перестала быть строго
выпуклой, пример отбрасывается до вызова дорогого решателя. Случайные параметры
получаются только из `seed + index`, поэтому повторный запуск воспроизводит тот
же набор.

В каталоге результата лежит по одному сжатому NPZ на sample и
`manifest.jsonl`. Канонический формат имеет `format_version=2`. Поля NPZ:

* `boundary_points [B,3]` — ресемплированный контур;
* `dense_boundary_points [N,3]` — более плотное исходное Fourier-представление
  в той же канонической системе координат;
* `query_points [Q,3]` и `signed_distance [Q]` — точки и целевые значения;
* `surface_vertices [V,3]`, `faces [F,3]` — сетка решателя;
* `normalization_center [3]`, `normalization_rotation [3,3]`,
  `normalization_scale` — преобразование
  `canonical = rotation @ (world - center) / scale`;
* `metadata` — JSON-строка с параметрами контура, solver, запросов и версией
  формата.

Все координаты и расстояния в NPZ канонические. Для возврата строки точек в
исходные мировые координаты используется
`world = (canonical * scale) @ rotation + center`; расстояние умножается на
`scale`. В metadata также сохраняются исходный и канонический векторы площади и
число попыток генерации.

Запросы смешивают равномерные точки в ограничивающем кубе и точки около
случайных граней поверхности. Расстояние считается до ближайшего
ориентированного треугольника. Его знак равен знаку скалярного произведения
между вектором от ближайшей точки треугольника к запросу и нормалью,
полученной из порядка вершин `faces`. Это **локальный signed distance**:
открытая поверхность топологически не разделяет пространство на внутреннюю и
внешнюю области, поэтому глобальная классификация знака для далёких точек не
определена. Единая ориентация контура +Z делает знак согласованным между
samples; менять порядок обхода границы после генерации нельзя.
Если нужны только пары «контур → сетка поверхности», разрешён `--queries 0`:
в NPZ остаются пустые массивы `query_points [0,3]` и `signed_distance [0]`.
Это существенно ускоряет массовую генерацию; SDF-точки понадобятся только для
обучения implicit baseline, но не для аппроксимации сохранённой сетки
полиномами Чебышёва.

Если оптимизатор сохранил OBJ, но не достиг заданной невязки, CLI возвращает
код `2`. По умолчанию генератор отклоняет такой sample, чтобы незавершённое
решение не стало обучающей целью. Флаг `--allow-unconverged` сохраняет его
явно; тогда `metadata.solver.converged` и `returncode` показывают статус.
Код `1` и отсутствие OBJ всегда считаются ошибкой генерации.

`manifest.jsonl` содержит относительные `path` (а также совместимый ключ
`file`), `sample_id`, `group_id`, `split`, seed, размеры сетки и основные параметры solver.
Для двух smoke samples первый элемент относится к `train`, второй — к `val`.
В малых наборах последние два примера получают `val` и `test`. Начиная с 20
samples разбиение детерминированно хешируется из seed и индекса в пропорции
примерно 90/5/5, поэтому соседние контуры не образуют один непрерывный split.

Знак является локальным свойством ближайшего лица, а не точным SDF до
гладкой предельной поверхности. У текущего C++ решателя также нет проверки
самопересечений всей поверхности и адаптивного сгущения по кривизне; эти
ограничения отражаются в качестве целевых mesh samples.
