# Массовая генерация пар «контур → поверхность Плато»

`scripts/generate_dataset_parallel.py` предназначен для долгого запуска на
десятках и сотнях тысяч контуров. Он вызывает C++-решатель в отдельных
процессах, но держит в очереди лишь небольшое число задач, поэтому список из
100 000 индексов не превращается в 100 000 тяжёлых `Future`-объектов.

Сначала должна существовать Release-сборка решателя:

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build -j6
```

Основной запуск:

```bash
python3 -u scripts/generate_dataset_parallel.py \
  --samples 100000 \
  --workers 6 \
  --output-dir dataset/plateau-100k
```

На macOS можно не давать компьютеру уснуть во время расчёта и одновременно
сохранить консольный журнал:

```bash
mkdir -p runs
caffeinate -i python3 -u scripts/generate_dataset_parallel.py \
  --samples 100000 --workers 6 \
  --output-dir dataset/plateau-100k \
  2>&1 | tee runs/plateau-100k-generation.log
```

Параметры по умолчанию для этого скрипта уже соответствуют задаче:

* 100 000 детерминированных контуров, seed 100000;
* 64 граничные точки после ресемплинга и сохранённые 128 исходных точек;
* выпуклые support-Fourier XY-кривые с пятью модами и Fourier-высота по Z;
* `graph`, `refine=2`, не более 1500 итераций, tolerance `1e-6`;
* нормализация в `[-1,1]^3` и векторная площадь вдоль `+Z`;
* `queries=0`: сохраняются контур и target mesh, без дорогого набора SDF;
* шесть workers при автоматическом выборе и не более двух ожидающих задач на
  worker;
* шарды по 1000 NPZ, то есть 100 подкаталогов вместо 100 000 файлов в одном.

Число workers имеет смысл подбирать по температуре и памяти компьютера.
Решатель однопоточный, поэтому обычно разумны 4–6 процессов. Увеличение выше
числа производительных CPU-ядер может лишь усилить конкуренцию за процессор и
диск.

## Возобновление и целостность

Каждый NPZ сначала полностью записывается во временный файл в том же каталоге
и только затем атомарно переименовывается. Родительский процесс по мере
готовности добавляет запись в `manifest.jsonl`. После `Ctrl+C`, сбоя worker или
перезапуска компьютера достаточно повторить **ту же команду**: готовые индексы
пропускаются, а завершённые NPZ, которые не успели попасть в manifest,
автоматически восстанавливаются.

`generation_config.json` фиксирует все параметры, влияющие на данные. Если
повторный запуск меняет, например, seed, refinement или число samples, скрипт
отказывается смешивать несовместимые данные и просит выбрать новый
`--output-dir`. Число workers, размер очереди и частоту progress-сообщений
можно менять между запусками.

При неудаче worker по умолчанию делает ещё одну детерминированную попытку с
другим Fourier-контуром для того же индекса; число повторов задаёт `--retries`.
Окончательно неудавшиеся индексы записываются в `failures.jsonl`, после чего
процесс возвращает код 2. Повтор той же команды снова пытается вычислить только
отсутствующие samples. Незавершившиеся решения по умолчанию не принимаются как
ground truth; включать `--allow-unconverged` для итогового обучающего набора не
рекомендуется.

Структура результата:

```text
dataset/plateau-100k/
├── generation_config.json
├── generation_summary.json
├── manifest.jsonl
├── failures.jsonl
├── shard-00000/sample_000000.npz ... sample_000999.npz
├── shard-00001/sample_001000.npz ...
└── ...
```

Manifest сортируется по индексу после штатного завершения. Split определяется
стабильным хешем `(seed, index)` и даёт примерно 90% train, 5% validation и 5%
test. `generation_summary.json` содержит итоговое число готовых и сошедшихся
примеров, распределение split, диапазон размеров mesh, время и скорость
последнего запуска — именно этот небольшой файл удобно прислать после расчёта.

## Локальная оценка стоимости

Контрольный запуск на текущей Release-сборке (Apple Silicon, 6 workers,
`refine=2`, `queries=0`) дал 1000/1000 успешных support-Fourier samples за 4.17
секунды, около 246 samples/s. Средний сжатый NPZ вместе с плотным контуром занял
16.92 КБ, весь каталог с учётом файловой системы — 20.5 МБ на 1000 samples.

Линейная оценка для 100 000 samples — примерно 7 минут и 2.0 ГиБ на этом же
компьютере. Для длительного запуска разумно закладывать 10–20 минут и до 2.5 ГиБ:
частота CPU, нагрев, антивирусная индексация и скорость диска могут снизить
темп. Скрипт печатает фактические samples/s и ETA в процессе.

Перед полной серией полезно проверить команду без решения:

```bash
python3 scripts/generate_dataset_parallel.py \
  --samples 100000 --workers 6 \
  --output-dir dataset/plateau-100k --dry-run
```

Отдельный пилот на 1000 примеров можно сделать в другом каталоге. Однако
100 000 — это верхний рабочий объём, а не доказанная минимальная потребность:
после обучения следует построить learning curve на поднаборах 1k, 10k, 30k и
100k. Если качество перестанет расти, полезнее расширять семейство контуров,
чем добавлять почти повторяющиеся эллиптические гармоники.
